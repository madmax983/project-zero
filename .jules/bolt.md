**[Bevy ECS HashMap Clone Bottleneck in refining.rs]
**Learning:** `world.query_filtered()` creates a mutable borrow over the `World` preventing concurrent immutable resource borrows like `world.get_resource::<T>()` inside closures. Developers often bypass this by cloning large resources (like HashMaps). However, `query.iter(world)` only requires an immutable world reference. By separating the query creation from iteration, you can fetch read-only resources immutably and perform a zero-allocation single-pass iteration using `filter_map`.
**Action:** When filtering a mutable ECS query based on a global resource, create the `QueryState` first, get the resource, and then use a single-pass iterator instead of cloning the resource or collecting an intermediate vector.
**[Avoiding Deep Copies of Global World State in Systems]
**Learning:** Cloning a massive struct (like an entire TerrainGrid's tiles array) every frame to access a few data points in read-only checks is a major performance bottleneck causing hundreds of heap allocations. The compiler/borrow-checker will let you do it if it's the simplest way to sidestep mutating `world`, but it's wildly inefficient.
**Action:** Always fetch the immutable World resource immediately before reading the necessary properties (scoping the read properly with a block if necessary) rather than cloning the resource and destructing it out before mutably querying the World later. This converts an O(N) heap allocation into a direct pointer read.
