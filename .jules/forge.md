**[God Functions in Movement and Arrival]**
**Learning:** `movement_system` in `movement.rs` and `process_arrival` in `arrival.rs` had grown into monolithic "God Functions", managing everything from coyote speed threshold checking, environmental penalty calculations, and executing deep `match` logic for specific arrival tasks (e.g., `ConsumeChemical`, `ScrawlMemeticSigil`). This excessive responsibility makes testing difficult, triggers `too_many_lines` clippy warnings, and masks core flow.
**Action:** Extract specific phases (e.g. `calculate_movement_cost`, `try_apply_movement_speed`) and large match arms (`handle_consume_chemical_arrival`, `handle_scrawl_memetic_sigil_arrival`) into helper functions using early returns. This flattens conditionals and transforms large functions into clear pipelines, allowing the removal of the clippy allow attributes.

**[God Functions and Pyramids of Doom in Farming]**
**Learning:** `consume_food_system` and `produce_food_system` in `src/layer1/agriculture/farm.rs` contained massively nested loop bodies and conditional structures that caused them to hit the `clippy::too_many_lines` threshold. Extracting the loop bodies into helper functions correctly simplifies the main logic. When extracting `Mut` types (e.g., `Mut<Needs>`) into function parameters, it's critical to add the explicit lifetime `'_` (e.g., `Option<Mut<'_, Wallet>>`) when wrapping it in other types like `Option` to satisfy Rust's borrow checker.
**Action:** Extracted the loops into `apply_food_consumption_effects` and `process_single_farmer` helper functions with correct `'_` lifetimes for `Mut` params. Allowed removal of the `too_many_lines` clippy allowance on the file.

**[God Functions in Input and UI Map]**
**Learning:** `handle_normal_mode` in `src/shared/input.rs` and `build_map_layer_spans` in `src/ui/map.rs` had grown into monolithic "God Functions", managing everything from speed changes, camera movement, rendering line spans, and various cursor checks. This triggered `too_many_lines` clippy warnings and made the functions hard to read. Furthermore, passing `GameKeyEvent` by value sequentially across extracted helper functions relies on it being `Copy` or taking ownership unnecessarily.

In future refactors involving event arguments, I should consider passing by reference (e.g. `&GameKeyEvent` or `key.code`) to extracted helper functions to avoid move semantics pitfalls.

**[Bevy 21-Parameter Schedule Limit]**
**Learning:** Bevy's `add_systems()` macro inside a `Schedule` can only handle tuples of up to 21 systems (or system sets). If a schedule block (like the ones in `src/layer1/systems/observation.rs`) exceeds this limit, it triggers an obscure, massive compiler error involving `NodeConfigs` and `IntoSystemConfigs` (or `IntoSystemSetConfigs`) failing to resolve.
**Action:** When encountering a massive type resolution error during `cargo clippy` or `cargo build` pointing to a system registration block, count the number of systems in the tuple. If it's more than 21, break it into two separate `schedule.add_systems((...).in_set(...));` blocks to satisfy the macro's limit.
